Mobile lesson 1 · Adaptive layout

Mobile responsiveness starts without breakpoints

Your tangible win: build the ordinary phone screen fluidly, then recognize the few cases where window size should change its structure.

Most React Native screens need no width query. Professionals first rely on Flexbox, intrinsic content size, wrapping, scrolling, safe areas, and the keyboard. They classify the window only when an alternate structure actually exists.

The four-step mental model

1. Window

2. Classifier

3. Screen
Which structure is useful here?

The operating system can resize the app because of rotation, an unfolded foldable, split-screen, or a desktop-style window. React Native's useWindowDimensions() observes that current app window and updates when it changes.

Concrete Sarflog example

390 × 844

Compact width. Show the expense list as one pane. Tapping an expense navigates to its details.

700 × 1000

Medium width. Keep one pane unless a specific screen proves a supporting pane is useful.

1024 × 1366

Expanded width. The expense list and selected expense details may appear side by side.

Notice what did not happen: the code never asked whether the hardware was an iPhone, Samsung phone, iPad, or foldable. It only asked how much usable space the app had.

The bad pattern

// Several unrelated screens
if (width > 700) ...
if (width > 735) ...
if (width > 720) ...

These unexplained values become “magic numbers.” Nobody knows which behavior owns them, and screens drift apart.

Breakpoints do less work than you think

Most responsiveness should come naturally from flex, wrapping, scrolling, safe areas, spacing tokens, and maximum content widths. Use a breakpoint only when the high-level structure changes—such as one pane becoming two.

// Mobile-first: base behavior works everywhere
<View className="flex-col gap-4 expanded:flex-row">
...
</View>

The unprefixed classes are the compact mobile layout. The expanded: variant activates only after the shared expanded boundary.

Android documents larger categories too, but Sarflog does not currently have behavior that needs them. An expanded layout remains capped instead of acquiring empty breakpoint tiers.

Retrieval practice

Without looking back, classify these windows using compact <600, medium 600–839, expanded ≥840:

  1. 430 × 932
  2. 700 × 1000
  3. 1000 × 700
Reveal after answering

430 is compact; 700 is medium; 1000 is expanded. Width and height are considered separately, so the third window is expanded width with regular height.

Primary reading: React Native Flexbox. Read React Native Dimensions only when the screen has a real alternate structure, and use Android window size classes as guidance rather than a requirement to implement every tier.
