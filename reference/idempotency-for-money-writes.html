Idempotency for money writes

Rule: repeating one logical command must produce the same business effect as executing it once.

The server decision

scope = (owner_id, operation, idempotency_key)
fingerprint = hash(canonical_request_payload)

New key

Reserve key, execute the write and its ledger effects in one transaction, then store the response.

Same key + same payload

Return the stored status and body. Do not execute domain logic again.

Same key + different payload

Reject the request. A key identifies one logical command, not a reusable client identity.

Non-negotiable details

  • Use a database uniqueness constraint on the complete scope; an application check alone races.
  • Persist the key record atomically with the payment, financial event, wallet movement, and ledger entry.
  • Define behavior for a duplicate arriving while the first request is still running.
  • Do not confuse idempotency with validation, transactions, locks, or UI button disabling.
  • Keep genuine repeated payments possible by giving each intentional payment a new key.
