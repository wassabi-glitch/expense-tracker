Lesson 5 · Payment Plan reliability

One payment, once—even when the request arrives twice

Your tangible win: decide whether a retry should create work, replay a result, or be rejected.

Idempotency is a business-effect guarantee. Sending the same logical command two or ten times leaves Sarflog as though it succeeded once.

The failure that matters

1.
App sends “record 200,000 UZS.”
2.
Server commits payment and ledger entries.
3.
Response is lost on a weak connection.
4.
App retries because it cannot know step 2 succeeded.

Without idempotency, the retry may subtract another 200,000 UZS from the wallet and add another payment entry. The request payload can be perfectly valid both times; validation cannot detect that both requests mean the same user action.

The key gives the command an identity

POST /payment-plans/42/payments
Idempotency-Key: pay_7f3...
{ amount: 200000, paid_date: "2026-07-17", ... }

Key unseen

Execute once and atomically store the result under the key.

Key seen, payload same

Replay the original result. Create no new financial effects.

Key seen, payload changed

Reject it. Reusing one identity for two commands is a client error.

Transaction ≠ idempotency

A database transaction answers: did this single attempt commit all its rows or none? Idempotency answers: are these two attempts actually one logical command? Sarflog needs both. The idempotency record, payment, financial events, wallet effects, and ledger entries must commit as one unit.

A “check then insert” in application code is insufficient: two concurrent requests can both observe no key. A database uniqueness constraint on a scope such as (owner_id, operation, idempotency_key) makes one contender win.

Apply it to Sarflog

POST /payment-plans/{plan_id}/payments is a natural protection boundary because it creates money history. A production design should specify key scope, payload fingerprinting, retention, concurrent in-flight behavior, response replay, and a database uniqueness constraint before implementation.

Primary reading: RFC 9110 §9.2.2, Idempotent Methods. For the emerging header protocol, see the IETF Idempotency-Key draft.
